# KnowledgeMap 集成 TradeSim 正式迁移计划

版本：2026-08-13

## 一、目标与边界

### 目标

- 将 `TradeSim` 正式并入 KnowledgeMap，成为门户中的一个完整业务模块。
- 前端统一由 KnowledgeMap 的 Vue/Vite 应用启动和管理。
- 后端统一由 KnowledgeMap 的 FastAPI 应用启动和注册路由。
- 保留 TradeSim 的回测、收藏、历史详情、AI 流式分析和策略代码。
- 保留 TradeSim 的数据完整性，并明确数据库、MongoDB、大对象日志的归属。
- 保留一份完整、可独立打包的 TradeSim 备份；打包备份与集成代码分开维护。

### 集成版本的非目标

- 集成版本不再单独启动 TradeSim 的 Uvicorn 进程。
- 集成版本不再由 TradeSim 自己托管前端静态文件。
- 集成版本不保留自动打开浏览器的 `run_app.py` 行为。
- 本阶段不实现“年线策略”；现有 `/yearline` 只是占位页。
- 本阶段不把 TradeSim 改造成多用户系统；保留当前 `user_id=0` 的语义。

## 二、迁移前必须确认的架构决策

以下事项在真正改代码前确认一次，避免迁移过程中反复重构。

- [ ] API 命名空间采用 `/api/tradesim/v1/...`。建议保留模块边界，不与 KnowledgeMap 现有 `/api/bills`、`/api/tags` 等路径混用。
- [ ] 前端路由采用 `/tradesim` 作为父路由：
  - `/tradesim/simulate`
  - `/tradesim/dashboard`
  - `/tradesim/detail/:id`
  - `/tradesim/yearline`
- [ ] 推荐暂时保留 TradeSim 的独立数据边界：同一个 MySQL 服务中继续使用独立的 `tradesim` 数据库，并继续使用独立的 MongoDB database/collection。应用进程统一，数据表和会话隔离。
- [ ] 如果最终要求把所有表都合并到 `knowledgemap` 数据库，需要另开数据库重构阶段，不能在复制代码时顺手处理。
- [ ] 集成版本只支持开发/服务器运行模式；SQLite、本地 JSON、PyInstaller 相关逻辑只保留在独立打包备份中。
- [ ] TradeSim 的 Element Plus 浅色界面是否原样保留。建议第一阶段保留业务界面，只做容器和样式隔离；统一视觉主题放到后续阶段。

## 四、目标目录结构

### 4.1 后端

TradeSim 不能继续以顶层 `backend/app` 的独立包形式直接复制，因为 KnowledgeMap 已经存在同名的 `app` 包、`main.py`、数据库和路由注册入口。

建议归入功能模块目录：

```text
backend/app/
├── routers/                         # KnowledgeMap 现有路由
├── models/                          # KnowledgeMap 现有模型
├── schemas/
├── crud/
└── tradesim/
    ├── __init__.py
    ├── router.py                    # TradeSim 路由总注册文件
    ├── api/
    │   └── v1/
    │       ├── ai.py
    │       ├── records.py
    │       └── simulate.py
    ├── core/
    │   └── config.py
    ├── db/
    │   ├── models.py
    │   └── session.py
    ├── schemas/
    │   ├── record.py
    │   └── simulate.py
    ├── services/
    │   └── data_fetcher.py
    └── strategy/
        ├── base.py
        └── specific/
            └── grid_trade.py
```

### 4.2 前端

建议使用功能目录，避免与门户的 `Dashboard.vue`、`App.vue`、`Notes.vue` 等文件混淆：

## 五、阶段 1：后端代码归并与路径改造

- [ ] 将 `core`、`db`、`schemas`、`services`、`strategy` 复制到 `backend/app/tradesim/` 对应目录。
- [ ] 不复制 TradeSim 的 `backend/main.py` 作为第二个入口。

- [ ] 将 TradeSim 的路由聚合逻辑整理为 `backend/app/tradesim/router.py`，由主应用统一 include。

### 5.2 Python import 路径逐项修改

所有 TradeSim 内部导入都必须从顶层 `app.*` 改为明确的 `app.tradesim.*`，例如：

- `app.api.v1.simulate` → `app.tradesim.api.v1.simulate`
- `app.api.v1.records` → `app.tradesim.api.v1.records`
- `app.core.config` → `app.tradesim.core.config`
- `app.db.session` → `app.tradesim.db.session`
- `app.db.models` → `app.tradesim.db.models`
- `app.schemas.simulate` → `app.tradesim.schemas.simulate`
- `app.strategy.base` → `app.tradesim.strategy.base`
- `app.strategy.specific.grid_trade` → `app.tradesim.strategy.specific.grid_trade`

重点检查：

- `simulate.py` 的策略导入和分发。
- `records.py` 的数据库 session、模型和配置导入。
- `ai.py` 的配置和 OpenAI 客户端导入。
- `grid_trade.py` 对 `BaseStrategy` 的导入。
- 测试脚本的 `sys.path` 和模块导入。

### 5.3 路由注册

- [ ] 在 TradeSim 模块内部为 `simulate`、`records`、`ai` 建立统一 router。
- [ ] 在 KnowledgeMap 的 `backend/main.py` 中追加 TradeSim router 注册。
- [ ] 统一最终路径为：
  - `/api/tradesim/v1/simulate/run`
  - `/api/tradesim/v1/records/save-favorite`
  - `/api/tradesim/v1/records/list`
  - `/api/tradesim/v1/records/detail/{record_id}`
  - `/api/tradesim/v1/ai/analyze-stream`
- [ ] 删除/不迁移 TradeSim 独立的 `/` 根路径响应，避免覆盖 KnowledgeMap 根页面。
- [ ] 删除 TradeSim 的 `allow_origins=["*"]`；CORS 由 KnowledgeMap 主应用统一配置。
- [ ] 保留统一 `/api/health`，如有需要再扩展为模块健康检查 `/api/tradesim/health`。

### 5.4 配置和生命周期

- [ ] 将 TradeSim 环境变量改为带模块前缀的名称，避免与 KnowledgeMap 冲突：
  - `TRADESIM_MYSQL_URL`
  - `TRADESIM_MONGO_URL`
  - `TRADESIM_MONGO_DB_NAME`
  - `TRADESIM_LLM_API_KEY`
  - `TRADESIM_LLM_MODEL`
  - `TRADESIM_LLM_BASE_URL`
- [ ] 集成版本移除 `APP_MODE=standalone` 分支；SQLite、本地 JSON 路径只留在独立备份。
- [ ] 不在模块 import 阶段执行不可控的数据库创建和外部服务连接；统一放入应用 lifespan 或可追踪的初始化流程。
- [ ] MongoDB client 在应用启动时初始化，在应用关闭时释放。
- [ ] AI client 尽量懒加载，并对未配置 Key、网络错误和超时返回明确错误。
- [ ] `DataFetcher` 当前会临时修改全局代理环境变量；并入门户后需要加锁或改成局部 HTTP 配置，避免多个请求并发时互相影响。
- [ ] 回测接口内部存在同步行情请求和 CPU 计算；正式集成时放入线程池/后台执行，避免阻塞账单、日历和 Dashboard API。
- [ ] 增加回测超时、并发限制和大数据量响应保护。

## 六、阶段 2：数据库和数据层处理

### 6.1 推荐的第一阶段数据方案

应用进程统一，但数据连接隔离：

```text
KnowledgeMap FastAPI
├── knowledgemap MySQL engine/session
│   └── tags, bills, calendar_events
└── tradesim MySQL engine/session
    └── simulation_records
        └── mongo_log_id → MongoDB tradesim.simulation_logs
```

- [ ] KnowledgeMap 原有 `engine`、`SessionLocal`、`get_db` 保持不变。
- [ ] TradeSim 使用命名明确的 `tradesim_engine`、`TradeSimSessionLocal`、`get_tradesim_db`。
- [ ] 不把两个项目的 `Base`、`metadata`、`get_db`、`engine` 直接混成同名对象。
- [ ] TradeSim 的 ORM 模型保留在 `app.tradesim.db.models`，避免和账单模型互相污染。

### 6.2 表结构核对和迁移

以实际数据库 `SHOW CREATE TABLE`/备份为准，不直接把旧的 `db_init.sql` 当作最终结构。需要重点核对：

- [ ] `simulation_records.mongo_log_id`：当前 ORM 模型有该字段，但现有 `TradeSim/db_init.sql` 中存在缺失风险。
- [ ] `data_frequency`：确认历史库是否已执行二阶段补丁。
- [ ] `annualized_return`、`strategy_params`、`created_at` 的默认值和精度。
- [ ] `BIGINT` 自增主键在 MySQL 中的行为。
- [ ] `symbol`、`total_return`、`created_at`、`mongo_log_id` 索引。
- [ ] JSON 字段在当前 MySQL 版本中的兼容性。
- [ ] MongoDB 中 `simulation_logs` 文档与 SQL 表的 `mongo_log_id` 是否存在孤儿记录或断链。

### 6.3 正式迁移流程

- [ ] 为 `simulation_records` 建立可追踪的增量迁移脚本；不要依赖 import 时的 `Base.metadata.create_all()` 代替生产迁移。
- [ ] 迁移前导出 `knowledgemap` 和 `tradesim` 的结构/数据备份。
- [ ] 如果已有 TradeSim 历史数据：迁移 SQL 索引记录，迁移或复用 MongoDB 大对象，并核对记录数、日志数、断链数。
- [ ] 设计失败回滚：新增字段和表可回滚；不直接执行删除旧表、覆盖数据库或不可逆数据变换。
- [ ] 明确是否补齐 Alembic。当前父项目文档提到 Alembic，但仓库中需要先确认是否已有完整 migration 目录。

### 6.4 集成版本与打包备份的数据模式

- [ ] 集成版本默认使用 MySQL + MongoDB。
- [ ] 独立打包备份继续使用 SQLite + 本地 JSON，不与集成版本共享运行目录。
- [ ] 集成版本不读取 `TradeSim/backend/data` 作为隐式数据目录。
- [ ] 如果未来需要集成版本也支持离线单机模式，另做“门户单机发行版”设计，不把两种模式混在本次迁移中。
