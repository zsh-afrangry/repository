## 2. 已确认的决定

> 本节是规则的**单一来源**。改规则改这里，其他章节只引用不重复。

### 2.1 数据模型

| 项 | 决定 |
|---|---|
| 事项类型 | **只有两值**：`todo`（待做事项）、`meeting`（安排）。原 `plan` 语义并入 `meeting`，`bill` 弃用 |
| 时间字段 | **`event_date` + `event_time` 两列**（不用单个 `DATETIME`） |
| `event_time` 为空时 | 判定到期时刻兜底为**当天 23:59:59** |
| 完成状态 | **`completed_at` 时间戳**，`NULL` = 未完成；撤销完成 = 置回 `NULL` |
| 过期精度 | 按**秒**计 |

**为什么 `completed_at` 而不是布尔值**：能回答"何时完成"；按完成时间过滤可回溯历史；
将来做趋势不必改表。存储成本差异（8 字节 vs 1 字节）可忽略。

**为什么保留两列而不是合并成 `DATETIME`**：不破坏既有契约——`CalendarEventOut` 的字段、
日历网格按 `event_date` 分组、`crud` 的排序都依赖它。代价是跨天比较必须集中在
一个函数里（`crud/calendar.event_due_at()`），**不要在各处手写两列比较**。

### 2.2 完成与达成的判定（最易错的一条）

`todo` 与 `meeting` 的**达成规则相反**：

| 类型 | 完成方式 | 时间过了意味着 |
|---|---|---|
| `meeting`（安排） | 时间去过了就算发生 | **算达成**——会开完了 |
| `todo`（待做事项） | 只能靠手动勾选 | **算失败**——超期未交 |

代码里分成两个函数，各回答一个问题：

- `is_overdue()` —— "时间过了没有"（与类型无关）
- `counts_as_progress()` —— "算不算达成"（**与类型相关**，规则相反）

⚠️ 若对 `todo` 也用"过期即达成"，**拖着不做的作业会让进度数字变高**，指标反而鼓励拖延。
已固化为回归用例 `calendar_crud_cases.py::test_todo_overdue_does_not_count_as_progress`。

### 2.3 「本周」的定义

**当前所在的日历周**：周一 00:00:00 → 周日 23:59:59。
即使今天是周六，"本周"也是到所在周的周日为止。
与前端日历组件的排布一致（Monday=0），后端由 `crud/calendar.week_bounds()` 统一计算。

### 2.4 待做卡片的取数与排序（第二轮）

**取数口径**：**未来 + 所有未完成**（不限日期）。
即：所有 `completed_at IS NULL` 的事项，无论日期在过去还是将来。

**为什么不用固定窗口**：固定窗口（本周 / 本月）会让**边界事项隐身**——
周五记"下周一交"，当天看不到；等看到时已经到期。
**越是需要提前准备的事越容易看不到**，这违背这张卡的存在意义。

**排序规则**：

```
1. event_time 为空的事项（极速录入 / 只填了标题）→ 全部排在最前；
   组内**最新的排最前**（次级键 -id，即创建时间倒序）
2. 其余按 (event_date, event_time) 升序
```

⚠️ **刻意不按 `event_date` 单独排序**：一条"只填标题、先记下来"的事项会排在
"昨天就该交的作业"之前。这是有意的——无时间的事项还没被规划过，需要先被看到
并决定何时做（清空收集箱）。而**已过期的欠账仍会在有时间的那组里排最前**。

⚠️ **「未安排」组内最新的在前**（用户 2026-10-07 决定）。这条是实测发现的：
原先两条无时间的事项排序键完全相同，`sorted()` 是**稳定排序**，
于是保留查询返回顺序（MySQL 按主键升序），结果**刚记的事沉到下面**——
用户会怀疑"到底记上了没"。选"最新在前"是因为刚记下的事需要立刻可见。

**摘要显示 `min(3, 总数)` 条**（用户例子验算：2 条无时间 + 明天 + 后天
→ 排序为「无时间、无时间、明天、后天」→ 取前 3 = **无时间、无时间、明天**）。

**必须同时显示分类总数**：摘要只显示 3 条，被截掉的事项会变成新的"隐身"。
所以卡片顶部要显示类似 **「今天 1 · 过期 2 · 未安排 3」**——
这样即使列表只有 3 行，也能一眼看出"还有 3 条没安排"。

**分类的判定在 `crud/calendar.pending_bucket()` 一处**（§11.6）：
分类计数与抽屉标签页的分组都从它派生，保证"角标数字 = 该页条数"。
⚠️ 三个分类**不是完整划分**——有时间的未来事项不属于任何一个（见 §11.6）。

**条数上限**：后端返回上限 **200 条**，超出时返回总数并提示，**不静默截断**。

### 2.5 「已作废」（已实施）

用户定位：**废纸篓 / 回收站**——可查看、可恢复，与"删除"不同（删除是真没了）。

| | 删除 | 作废 |
|---|---|---|
| 数据 | 真的没了 | 保留，可恢复 |
| 计入欠账 | 否 | **否**（这正是作废的目的） |
| 计入周进度 | — | **分子分母都不算** |
| 日历显示 | 不显示 | **照常显示** |
| 用途 | 记错了 | "我决定不做了" |

**为什么需要它**：现在"完成/未完成"二值，一条你**决定不做**的事会永远留在"已过期"里，
**污染欠账数字**。有了作废，"过期"才真正等于"需要处理的欠账"。

#### 用户确认的四条（2026-10-07）

| # | 决定 | 实现 |
|---|---|---|
| ① | 已作废的**分子分母都不算**，仅作展示 | `week_progress()` 过滤 `archived_at IS NULL` |
| ② | 每条最右侧一个「作废」按钮，**无二次确认**；点击后顶部弹提示（约 5 秒）**带「撤销」** | `PendingDrawer.vue` 的 `.drawer-item-action`；`PendingToast.vue` + `usePendingTasks.archiveItem()` |
| ③ | 抽屉里加**折叠区**查看与恢复 | `.drawer-archive`（`aria-expanded` 控制的折叠区） |
| ④ | 日历**照常显示**已作废的事项 | `list_calendar_events()` 不加过滤 |

**为什么敢不做二次确认**：作废**可逆**，而且立刻给出带「撤销」的提示。
确认框对高频操作是负担；**"可撤销的即时操作"比"每次都要确认"体验更好**。

**① 的副作用（用户已知并接受）**：作废一条超期作业会让完成率**变高**，
因为那条"失败"被移出分母。理论上"全部作废"也能得到 100%——
用户判断这在个人日常使用中不会发生，且废纸篓内容始终可见。

#### 数据与查询

- 新增列 `archived_at DATETIME NULL`（NULL = 未作废）。
- **所有"未完成"查询**的条件是 `completed_at IS NULL AND archived_at IS NULL`，
  集中在 `crud/calendar.pending_events()` 一处。
- `week_progress()` **单独**过滤已作废（它不走 `pending_events()`，因为周窗是另一套口径）。
  这两处是仅有的两处需要排除已作废的地方。

⚠️ **`week_progress()` 的过滤曾漏掉**（2026-10-07）：测试先断言"作废后分母减 1"才暴露出来。
若没这条断言，作废后完成率会**静默地不变**。回归固化在
`calendar_crud_cases.py::test_archived_does_not_count_toward_week_progress`。

**作废 ≠ 完成**：两者互不影响。一条已完成的事项也可被作废；
一条已作废的事项可能曾经完成过（`completed_at` 不会被作废操作清掉）。

### 2.6 其他

| 项 | 决定 |
|---|---|
| 「本周进度」 | **保持独立**，不随待做卡片改口径。它回答"这周做得怎么样"（周报），卡片回答"我还有什么没做"（清单） |

| 脚本落位 | 辅助脚本进 `backend/scripts/`，测试进 `backend/tests/`；**根 `scripts/` 不再新增** |

## 3. 数据模型

### 3.1 `calendar_events`（当前结构）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | int PK | |
| `event_date` | date, indexed | 事项日期；日历按此加载与标记 |
| `event_time` | time NULL | 为空表示当天未指定时刻，判定过期时兜底 23:59:59 |
| `title` | varchar(128) | 标题 |
| `detail` | text NULL | 说明 |
| `tone` | enum('todo','meeting') | 事项类型 |
| `completed_at` | datetime NULL | 完成时间；NULL = 未完成 |
| `archived_at` | datetime NULL | **作废时间；NULL = 未作废**（2026-10-07 新增，见 §2.5） |
| `created_at` / `updated_at` | datetime | |

**`completed_at` 与 `archived_at` 是两件独立的事**：
完成 = 做到了；作废 = **我决定不做了**。两者互不影响，可以同时存在。
判断"是否还要做"要同时看两个字段（见 §2.5）。

**列注释随导出进入版本控制**，是结构文档的一部分。
⚠️ 2026-10-06 踩过：第一次重建表时模型里漏写 `comment=`，导致原库 9 列注释**全部丢失**。
**改列时不要漏掉 `comment=`。**

### 3.2 表结构管理

**权威来源是 SQLAlchemy 模型**（项目刻意不用 Alembic）。`create_all()` 只创建缺失的表、
**不会 ALTER 已有表**，所以结构变更过去只能靠人记得手动执行 SQL。

现在结构随 git 版本控制：

| 产物 / 脚本 | 作用 |
|---|---|
| `backend/sql/knowledgemap.sql` | 全库 6 张表的快照（`--no-data`），含列注释 |
| `backend/scripts/export_schema.py` | 生成上表；`--check` 检测漂移（有差异退出码 1） |
| `backend/scripts/rebuild_calendar_events.py` | 单表结构变更的范例：只碰一张表、拒绝在非空表上运行、检测列注释漂移、幂等。**期望结构从模型推导**（不写死列名），所以任何一次加列都能直接用它 |

**两条注意事项**：

1. ⚠️ `backend/sql/knowledgemap.sql` **含全部 6 张表的 `DROP TABLE`**。
   直接执行会连 `bills`（真实账单）和 `notes_topics`（种子数据）一起删掉。
   **单表变更要写针对性脚本，不要跑这个文件。**
2. 导出会抹平 `AUTO_INCREMENT` 计数与时间戳等噪声，使 `git diff` 只反映真实结构变化。
3. ⚠️ **迁移脚本曾经写死列名**（第一版硬编码 `completed_at`），于是 2026-10-07 再加
   `archived_at` 时它会误报"已是最新结构"——每加一列就得改一次脚本，等于把模型结构抄了两份。
   现已改为**与模型比对列名集合**：缺任何一列、或库中多出模型没有的列都会报告。
   加列时直接跑它即可，不要新建脚本。

**与根 `表结构/` 的关系**：那是 2026-07-05 由 Navicat 导出的历史快照（只含 3 张表，
与当前代码已不一致），保留作史料但**不再维护**；`backend/sql/` 是随代码自动导出的现行快照。
**旧脚本含 DROP，禁止对真实库执行。**

## 4. 统计口径

### 4.1 本周进度

**分母** = 本周所有事项（`todo` + `meeting`）**，排除已作废**
**分子** = 本周事项中"算作达成"的数量（判定见 §2.2）

⚠️ **已作废的事项分子分母都不算**（用户 2026-10-07 决定，见 §2.5）。
作废 = "我决定不做了"，它不是承诺，不该出现在任何达成率里。

⚠️ **分母为 0 时 `ratio` 返回 `null`**（不是 `0`、不是 `NaN`）。
周一早上必然为空，而 `(0/0)*100` 得到 `NaN`，会让 `stroke-dasharray="NaN, 100"` 整个失效。
前端据此显示 `--` 并画 0 长度弧。用例断言响应体**不含 `NaN` 字面量**。

**返回字段**：`start` / `end` / `total` / `done` / `overdue` / `numerator` / `ratio`。

⚠️ `overdue`（时间过了且未完成）与 `numerator`（算作达成）是**两个不同的数**，别混用：

| 字段 | `todo` 过期 | `meeting` 过期 |
|---|---|---|
| `overdue` 计入 | ✅ | ✅ |
| `numerator` 计入 | ❌ | ✅ |

### 4.2 代码量口径

**只算源码后缀**（`.py` `.ts` `.vue` `.css` `.sh` `.js`），**按月**，取**净变化**（新增 − 删除）。

- 刻意**不含 `.json`**：否则 `package-lock.json` 的一次更新就能让数字暴涨几千行。
- 刻意**不含 `.md`/`.txt`**：文档字数不是代码量。

**必须排除的目录**（`EXCLUDED_PATHSPECS`）：

```
:(exclude)frontend_example/**     ← 20 个 vendored 示例文件全是 .js/.css
:(exclude)已归档/**
```

⚠️ **排除项看起来"多余"时最危险**：本月数字在排除前后**完全相同**（都是 551），
因为它防的是**将来**动 `frontend_example/` 的情况。
实测（全量历史）：不排除 25897 行 vs 排除 18942 行，**相差 6955 行**。
删掉它当月毫无症状，下次那个目录被改动时数字才悄悄失真。

`app/git_stats.py` 与 `scripts/code_volume_probe.py` 里的常量**必须保持一致**，
否则工具与实现会给出不同答案。

**提交数口径**：统计**全部**提交（含只改文档的），与行数的范围不同，因此是两次 git 调用。
提交数用 `--pretty=tformat:<marker>` 数标记得到（实测与 `git rev-list --count` 一致），
耗时约 180 ms。

## 5. 接口设计

### 5.1 `GET /api/dashboard/overview/`

一次返回首页四张卡的全部数据（首屏一次请求，避免各卡分别 loading 造成跳动；
口径与除零逻辑集中在后端一处）。

```jsonc
{
  "week": {
    "start": "2026-10-05", "end": "2026-10-11",
    "total": 6,        // 分母
    "done": 1,         // 其中手动完成
    "overdue": 2,      // 其中时间已过且未完成（仅供展示）
    "numerator": 2,    // 分子：算作达成
    "ratio": 33.3      // 分母为 0 时为 null
  },
  "stats": {
    "code_lines":  { "period": "month", "month_start": "2026-10-01",
                     "added": 2714, "deleted": 2163, "net": 551, "binary_files": 0 },
    "notes_units": { "topics": 7, "sections": 17, "units": 31 },
    "git_commits": { "month": 3, "total": 70 }
  }
}
```

**降级**：git 不可用时 `code_lines` 与 `git_commits` 返回 **`null`**（HTTP 仍 200），
前端显示 `--`。`null` = 取不到，`0` = 真的是零。

### 5.2 `GET /api/dashboard/pending/`

待做清单 + 废纸篓：**所有未完成的事项，不限日期**（口径与排序见 §2.4）。

单独一个端点而不是只放在 `overview` 里的原因：勾选完成、新增或**作废**后，
只需刷新清单，不必重取 git 统计与 Notes 汇总（那两项开销大且不会因此变化）。

`overview` 的响应里也带同一份 `pending` 与 `archived`（由**同一个** `_build_pending()` /
`_build_archived()` 生成，不会分叉）——首屏一次请求就能拿到全部内容。

```jsonc
{
  // —— 待做清单 ——
  "total": 6,        // 未完成事项的**真实总数**（可能大于 items.length）
  "shown": 6,        // 本次实际返回条数
  "counts": { "overdue": 2, "today": 1, "unscheduled": 3 },
  "truncated": false, // true = 因超过上限被截断，前端**必须提示**
  "items": [ /* CalendarEvent[]，已由后端排好序；前端不要再排序 */ ],

  // —— 废纸篓（2026-10-07 新增）——
  "archived": {
    "total": 2,
    "shown": 2,
    "truncated": false,
    "items": [ /* 按**作废时间倒序**（最近作废的在前） */ ]
  }
}
```

**`archived` 为什么没有 `counts`**：`overdue`/`today`/`unscheduled` 那套分类是给
待办优先级用的（"哪件更急"），废纸篓不需要——里面的东西已经不需要做了。

**两者一起返回的原因**：抽屉里"待做列表"与"已作废折叠区"是同一屏，
分两次请求会在作废/恢复的瞬间产生中间态（列表已更新、折叠区还是旧的）。

**分类计数的语义**（互不重叠，按优先级判定）：

| 优先 | 分类 | 判定 |
|---|---|---|
| 1 | `overdue` | `is_overdue()`（时间已过且未完成） |
| 2 | `unscheduled` | `event_time IS NULL`（极速录入的产物，需要被安排） |
| 3 | `today` | `event_date == 今天` |

⚠️ **三者之和 ≤ `total`**：有时间的未来事项不占任何分类（不紧急，不需要在摘要里占注意力）。
前端**不要**假设它们相加等于总数。

**每条 `items[]` 还带一个 `bucket` 字段**（`'overdue'` / `'today'` / `'unscheduled'` / `null`），
与 `counts` 由**同一个** `pending_bucket()` 派生。
抽屉的标签页按它过滤（`bucket === 当前页`），所以**该页条数必然等于角标数字**。
`bucket: null` 表示"有时间的未来事项"，只在「全部」页出现（见 §11.6）。

⚠️ `unscheduled` 排在 `today` 之前是刻意的：只填了标题、默认落在今天的事项，
应被算作"待安排"而不是"今天要做"——"未安排"这个数字正是用来提醒你去安排的。

### 5.3 日历事项

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/calendar-events/?date_from=&date_to=` | 区间查询（日历网格用） |
| POST | `/api/calendar-events/` | 新建 |
| PATCH | `/api/calendar-events/{id}` | 通用更新（**前端尚未接编辑**） |
| PATCH | `/api/calendar-events/{id}/completion` | `{done: bool}`；**服务端填时间戳** |
| PATCH | `/api/calendar-events/{id}/archive` | `{archived: bool}`；作废/恢复，**服务端填时间戳** |
| DELETE | `/api/calendar-events/{id}` | 删除（**真删**，与作废不同） |

**为什么 `completion` 与 `archive` 是专用端点而不是走通用 `PATCH /{id}`**：
两者都是高频单一意图，若由前端传时间戳，客户端时钟与服务端不一致时会写进错误时间。
只传布尔意图、时间由服务端取，也更利于"撤销"——前端不必记住原值。

⚠️ **日历的区间查询不过滤已作废**（用户 2026-10-07 决定）：已作废的事项**照常显示**。
理由：它确实占用过那天，抹掉会让日历与你对那天的记忆不符。

### 5.4 跨模块取数（Notes 单元数）

「笔记与文档」的数据在 `notes_topics` 表，`data` 是 **JSON 列**，
单元数是 Python 侧 `len(data["units"])` 数出来的，**没有 SQL 聚合可用**。

**方案**：计数实现归 Notes 模块所有（`app/notes/aggregates.py`），
dashboard 只调 `count_all(db)`；`list_topics` 也改用同一个 `topic_counts()`。

若 dashboard 直连该表并自己解析 JSON，会**复制** Notes 的数据结构知识——
一旦 Notes 改结构就会在**运行时**才炸，且报错离原因很远。现在的耦合是"一行函数调用"。

### 5.5 保留的旧端点

`GET /api/dashboard/git-stats/` 保留不动（兼容既有调用）。
新代码请用 `/overview/`。

## 6. 前端实现

### 6.1 四张卡

| 卡片 | 数据源 |
|---|---|
| 天气 | `GET /api/weather/`（可切换城市，见 `docs/12`） |
| 日历（网格 + 弹窗） | `GET /api/calendar-events/` |
| 日历卡片底部「今日安排」 | 同一份 `calendarEvents`，取**今天**的 |
| 待做事项 | `GET /api/dashboard/pending/` —— **不依赖 `calendarEvents`**（见 §11.1 缺陷 2） |
| 本周进度 | `overview.week` |
| 待做抽屉 | `/dashboard/pending/`（与卡片共享 `usePendingTasks()`，见 §6.4） |

**待做卡片的呈现**（§2.4）：摘要显示前 3 条 + 分类计数 + 未完成总数；
超出上限时显示"仅显示前 N 条"。**截断必须可见**——静默截断会让事项变成看不出来的"隐身"。

### 6.2 前端不重算口径

分子/分母、除零、排序都由后端算。原因：口径里有两处易错逻辑
（两类 `tone` 的达成规则相反、跨天过期比较），放前端算等于把规则抄一遍，两边迟早不一致。

**唯一例外**：前端有自己的 `isEventOverdue()`，用来决定**是否显示「过期」标记**。
它与后端 `counts_as_progress()` **刻意不同**——前者回答"时间过没过"（两类都标），
后者回答"算不算达成"（按类型分规则）。代码注释里写明了，**不要"统一"它们**。

### 6.3 交互细节

| 项 | 实现 |
|---|---|
| 「＋」弹窗 | 复用日历弹窗的全部样式类；类型下拉 `todo`/`meeting`；`<input type="datetime-local" step="1">` |
| 勾选 | **乐观更新 + 失败回滚**；成功后用服务端返回的时间戳覆盖本地猜测值 |
| 「今日安排」 | 消费真实数据；空时显示"今天没有安排。" |
| 待做抽屉 | 挂 `App.vue`（全局可达）；`Ctrl/Cmd+K` 或卡片「查看全部 →」唤出；见 §11.2 |

### 6.4 全局状态：`usePendingTasks()`

待做清单有**两个消费方**（首页卡片、全局抽屉），必须共享同一份状态——
在卡片上勾掉一条，抽屉里也要立刻消失，否则用户会怀疑哪边是真的。

**实现**：`composables/usePendingTasks.ts` 用**模块级 `ref`**。模块只求值一次，
所以所有调用者天然共享同一批 ref。项目没装 Pinia，不值得为此引入依赖。

⚠️ **不要在组件里 `ref()` 一份本地副本**——那会让两边各自持有状态，
勾选后只有一边更新，正是 §11.1 缺陷 2 那类"两套数据源"问题的翻版。

**职责边界**：本模块只负责**取数与缓存**，**不做过滤或重排**——
口径与排序是后端的（§2.4）。

### 6.5 全站提示（`AppToast.vue`）

**一处实现，两个使用方**：作废提示（5 秒 + 「撤销」）与主题按钮的"功能待开发"提示（3 秒）。
共用 `composables/useToast.ts`（模块级单例）与 `AppToast.vue`（挂 `App.vue`）。

| 项 | 做法 |
|---|---|
| 位置 | `top: 10%`、窄屏（≤720px）`8%`；`left:50%` + `translateX(-50%)` 水平居中 |
| ⚠️ 动画 | 进出场**必须写成 `translate(-50%, …)`**——基类已用 `translateX(-50%)` 做居中，只动纵向会丢掉居中、提示从视口左侧滑入 |
| 倒计时条 | 底部一条从 100% 缩到 0 的 2px 渐变线，走完提示即消失 |
| ⏸ 暂停 | 悬停或键盘聚焦时**暂停**（移开 / 焦点离开后按剩余时间继续） |

**为什么倒计时条与计时器必须共用同一个值**：进度条是 CSS 动画、关闭靠 JS 定时器，
是两套时钟。两者都取 `durationMs`（见 `useToast`），改时长不会只改一半。
`:key` 递增会让 Vue 重建元素，从而让进度条动画重新开始。

**为什么悬停必须暂停**：提示里可能有「撤销」按钮。若倒计时照走，用户正要点时弹窗先消失，
就点空了。键盘用户更明显：Tab 到按钮上时弹窗消失，等于这个按钮不可达。

**为什么 `prefers-reduced-motion` 下仍保留进度条**：它是**信息**（还剩多久）不是装饰，
所以只去掉进出场动画，不像页面滚动那样整个关掉。

**浏览器实测**（进度条必须真的在缩，不能只验 CSS 属性）：

| 采样时刻 | 进度条宽度 | 提示宽度 |
|---:|---:|---:|
| 0.0s | 331.7px | 353.2px |
| 0.5s | 269.2px | 353.2px |
| 1.0s | 212.6px | 353.2px |
| 1.5s | 154.1px | 353.2px |
| 2.0s | 91.7px | 353.2px |

线性缩短；3 秒后提示消失。悬停时宽度**完全不变化**（290.7px → 290.7px），
且超过原时长仍不消失。

⚠️ **没有引入 toast 库**（vue-toastification / react-toastify 等都有这条进度条，
`hideProgressBar` 默认 `false`）。理由：① 门户是纯自定义深色设计系统，
库自带的浅色 Material 样式要全部覆盖（Element Plus 就是因此被隔离在 TradeSim 模块）；
② 需要的功能总共不到 100 行；③ 进度条与倒计时要共用时长常量，自己写才保证这一点。

**顺带修掉的不一致**：主题提示原先内联在 `Dashboard.vue`，所以**只在首页**能出现；
作废提示是全站的。合并后两者都在任何路由可用。

## 11. 待做事项的设计与路线

本节回答"待做事项该住在哪里"（用户的原始问题），并记录每层的实施状态。
L1 与 L2 已落地；L3 与「已作废」是明确的后续方向。

### 11.1 第二轮修掉的两个缺陷（已完成，2026-10-07）

| # | 缺陷 | 成因 | 修法 |
|---|---|---|---|
| 1 | 卡片只显示当前自然周的事项 → "下周一交作业"看不到 | 用了固定窗口 | 改为 `pending_events()`：所有未完成事项，**不限日期** |
| 2 | **卡片数据源绑定在"日历当前可见月份"上** → 翻月就变空 | 卡片遍历 `calendarEvents`（只装了 `getVisibleCalendarRange()` 那段日期），而进度数字来自后端独立查询——**两者是两套窗口** | 卡片改消费 `GET /dashboard/pending/`，不再依赖日历的加载范围 |

> 缺陷 2 是复核时发现的，用户未提到。它比缺陷 1 更隐蔽：**没有任何报错提示**，
> 只是卡片悄悄变空，而同一张卡上的进度数字仍然正常。

**浏览器实测对照**（同一条"下周一"的事项）：

| | 修复前 | 修复后 |
|---|---|---|
| 该事项 | ❌ 不显示 | ✅ 显示 |
| 点「下个月」后 | ❌ 卡片变空（`0/1` → `0/0`） | ✅ 内容不变 |

### 11.2 待做事项的三层结构（L1/L2 已实施）

用户判据：**随时点击就能看到、详细且直观**。

**关键矛盾**：既要"随时可达且不打断当前工作"，又要"装得下更多信息且能管理"。
路由跳转会卸载当前页面（看笔记看到一半跳走再回来，状态可能丢失），
所以**单一形态无法同时满足**——必须分层。

| 层 | 形态 | 解决什么 | 状态 |
|---|---|---|---|
| **L1 卡片** | 首页摘要，显示 3 条 + 分类计数 + 总数 | **扫一眼**：今天要做什么 | ✅ 已实施 |
| **L2 侧拉抽屉** | 右侧滑出 27rem，**盖住而非跳转**，`Ctrl/Cmd+K` 唤出；内含 **4 个标签页** | **随时查看 + 快速操作**（含作废、废纸篓折叠区） | ✅ 已实施 |
| **L3 `/tasks` 路由** | 全页 | **管理与回顾**：筛选、批量、统计 | ⬜ 未实施 |

**为什么 L2 是抽屉而不是路由**：抽屉一步可达、**不卸载当前页**，这是日常最高频场景。
**为什么仍需 L3**：抽屉空间不够做"每周整理积压"这类管理动作（批量改期、归档、清理）。
**为什么保留 L1**：首页需要"不点击就能看到"——卡片是摘要，抽屉是全量。

### 11.6 抽屉的标签页（已实施）

用户决定的分组（2026-10-07）：**全部 / 今天 / 已过期 / 未安排**。废纸篓仍是底部折叠区。

#### ⚠️ 「全部」页是**必需的兜底**，不是可选项

三个分类**不构成完整划分**。实测：5 条事项里只有 3 条落进分类，
**「下周一 14:00 交作业」落不进任何一个**——它没逾期、不是今天、又有具体时间。

若标签页只按三个分类切，这类事项会在**每个**标签页里都看不见——
那正是第二轮"固定窗口让边界事项隐身"那个缺陷的翻版。
所以「全部」必须存在，且**默认选中**。

#### 分桶判定在后端（关键设计）

`crud/calendar.pending_bucket()` 是**唯一**的判定处：

- `pending_summary()` 的 `counts`（角标数字）从它派生；
- 每条事项的 `bucket` 字段也从它派生，前端按 `bucket === 当前页` 过滤。

于是「角标数字」与「该页条数」**在构造上不可能不一致**。
若让前端自己写过滤条件，两者迟早分叉——这正是 §12.5 记下的教训。

**不变量已固化为用例**：`calendar_crud_cases.py::test_bucket_counts_are_complete_partition_of_bucketed_items`
断言每个桶的角标 = 该桶条数，且三桶之和 + 无桶项 = `total`。

#### 空页提示必须区分

「全部」为空 = **真的**没有待做事项；分类页为空 = 只是这页没有，别处还有。
后者要提示"看看「全部」"，否则用户会以为事情做完了。

| 桶 | 判定 | 角标 | 用户该做什么 |
|---|---|---|---|
| `overdue` 已过期 | `is_overdue()` | `counts.overdue` | 补做，或改期 |
| `today` 今天 | `event_date == 今天` | `counts.today` | 今天做 |
| `unscheduled` 未安排 | `event_time IS NULL` | `counts.unscheduled` | 安排一个时间 |
| （无桶） | 有时间的未来事项 | 只在「全部」 | 不紧急 |

优先级与互斥规则同 §2.4 的分类计数（`overdue` > `unscheduled` > `today`）。

**废纸篓不进标签页**：它是"需要时才看"的内容，保留为底部折叠区。
当前实现把它写成独立的 `<section>`（内容与"折叠"这个外壳分开），
将来若要改成第 5 个 tab，只需换外壳、内容不用动。

**L2 的实现要点**

| 项 | 做法 | 原因 |
|---|---|---|
| 挂载位置 | `App.vue`（**根组件**） | 抽屉的判据是"随时可达"，所以唤出入口必须与路由无关 |
| 唤出方式 | `Ctrl/Cmd + K`，以及首页卡片的「查看全部 →」 | 快捷键要能在任何页面用；卡片入口是给不知道快捷键的人 |
| 组件挂载 | **常驻挂载**，由内部 `v-if` 控制面板显示 | `useDialogFocus` 依赖 `watch(open)`；若连组件一起 `v-if` 掉，Escape 与焦点陷阱会失效 |
| 状态共享 | `composables/usePendingTasks.ts`（**模块级 ref 单例**） | 卡片与抽屉必须看到同一份数据；勾掉一条两边都要变。项目没装状态库，不值得为此引入依赖 |
| 焦点/滚动 | 复用 `useDialogFocus` | 与日历弹窗、加号弹窗同一套：Escape 关闭、Tab 焦点陷阱、锁 body 滚动、关闭后焦点归位 |
| 样式 | 复用弹窗的遮罩视觉（深色 + 模糊）+ `UiButton` | 与全站一致；**不引入 Element Plus**（它只在 TradeSim 模块用，门户是纯自定义深色设计系统） |

⚠️ **不要把待做清单的数据再塞回 `calendarEvents`**：那正是第二轮修掉的缺陷 2
（卡片绑定日历可见月份，翻月就变空）。抽屉与卡片都走 `usePendingTasks()` → `/dashboard/pending/`。

### 11.3 极速录入（已实施）

用户三个判据都在说"看"，但**待办系统真正会失败的地方是"记下来"那一步**：
如果记一条需要"回首页 → 点加号 → 选类型 → 填标题 → 选时间 → 保存"六步，
那么**忙的时候就不会记**，数据是空的，后续所有查看功能全部白搭。

抽屉里的实现：

- **一个输入框 + Enter 即保存**，不要求选时间（类型默认 `todo`）
- **时间留空 = 未安排**：后端会把它排在清单最前（§2.4），界面标「未安排」——
  这正是提醒你"该安排它了"的信号。强行要求先选时间会让人放弃记录。
- 打开抽屉时**自动聚焦输入框**（打开就能打字）
- `Ctrl/Cmd + K` 从任何页面唤出

**为什么"不要求选时间"是关键设计**：用户此刻往往只知道"有这件事"，还不知道什么时候做。
允许留空是**为了不打断记录动作**——安排是第二步，可以之后再做。

**后续可加**（未实施）：自然语言简写（如"周五 交作业"）、快捷日期按钮（今天/明天/下周）。

### 11.4 数据模型的前瞻（现在不加）

若将来 L3 需要"按项目归档"，可能需要 `project_id` / `tag_id`、
`archived_at`（§2.5）、可选 `priority`。

**现在都不加**：① 还没有真实使用数据，加了大概率猜错；
② 加字段成本很低（有迁移脚本范例）；③ 过早设计会让表变复杂而收益不明。

### 11.5 落地顺序

| 阶段 | 内容 | 状态 |
|---|---|---|
| 1 | 卡片改名 + 修两个窗口缺陷 | ✅ 第二轮 |
| 2 | **L2 抽屉 + 极速录入** | ✅ 第三轮 |
| 3 | 「已作废」状态（§2.5） | ✅ 第四轮 |
| 4 | **抽屉标签页**（§11.6） | ✅ 第五轮 |
| 5 | **L3 `/tasks`**（筛选、批量、回顾、统计） | ⬜ 剩下唯一一项 |

**为什么「已作废」排在 L3 之前**：它会改变"什么算未完成"的定义
（`completed_at IS NULL` → 再加 `archived_at IS NULL`）。
先定下这个口径，L3 的筛选条件才能一次写对，不用回头返工。
好在查询已集中在 `pending_events()` 一个函数里，改动只影响一处。

**为什么标签页排在 L3 之前**：它是对现有高频界面的直接改进（几步就能切到"该做什么"），
而 L3 的筛选条件仍需真实使用数据才能定。

**为什么 L3 仍然放最后**：还不知道真实使用时哪些筛选最常用——先做全页容易把力气
花在用不上的功能上。抽屉已经覆盖了日常高频场景（记一条 / 看一眼 / 按状态切）。

⚠️ **做 L3 时要注意**：三个分类**不是完整划分**（§11.6），
所以 L3 的筛选也必须有"全部"这一类，否则有时间的未来事项会被筛没。

## 12. 开发记录

只记录**会影响将来判断**的事实：踩过的坑、环境约束、以及为什么某些决定不能改。

### 12.1 环境约束（非项目缺陷）

**DSH 沙箱注入的 `NO_PROXY` 会破坏 httpx。** 值含 `[::1]`（带方括号的 IPv6 字面量），
httpx 解析成 `all://*[::1]` 后把 `[:1]` 当端口，抛 `InvalidURL: Invalid port ':1]'`。
由于 `app/tradesim/api/v1/ai.py` 在**模块导入期**就构造 `AsyncOpenAI(...)`，
连 `import main` 都会失败。

| 尝试 | 结果 |
|---|---|
| Python 里 `os.environ.pop(...)` | ❌ 沙箱把环境变量表做成了受控/只读视图，写入后立刻读会 `KeyError` |
| `cmd /c` 包装脚本 | ❌ cmd.exe 用 GBK 读 UTF-8 的 `.cmd`，中文注释被当命令执行 |
| PowerShell 里设 `$env:NO_PROXY` | ❌ 同样受沙箱限制 |
| reload 子进程 | ❌ Windows 上 `multiprocessing.spawn` 从父进程原始环境块重建环境，Python 层修改不生效 |
| ✅ **导入前替换 `httpx._utils.get_environment_proxies`**，过滤含方括号的键 | 成功 |

**用户终端无此问题**，`python backend/main.py` 直接可用。

### 12.2 工具链的坑

| # | 现象 | 根因与对策 |
|---|---|---|
| 1 | 脚本崩 `UnicodeEncodeError: 'gbk' codec can't encode '\u2713'` | **Windows 控制台是 GBK**。新脚本一律用 ASCII 标记 `[OK]`/`[!!]`，不要用 ✓✗ |
| 2 | 迁移脚本误报 `tone 枚举需收敛: ['ENU']` | SQLAlchemy 的 MySQL inspector 对 `ENUM` **只返回字符串 `"ENUM"`，不含取值**。改读 `information_schema.COLUMNS.COLUMN_TYPE` |
| 3 | 断言"某文案已消失"时假失败 | 匹配到了**开发者自己写的说明注释**。断言前必须先剥掉 `<style>` 与 HTML 注释 |
| 4 | DOM 里 `class="stat-num"` 抓不到 | **Vue 的 scoped CSS 把 `data-v-xxxx` 插在 `class` 之前**。正则要容忍属性顺序 |
| 5 | 解析嵌套同名标签时漏抽 | `<tag>(.*?)</tag>` 配对写法遇到同名嵌套会提前停。改为"收集开始标签位置，内容 = 本标签结束 → 下一个开始标签" |
| 6 | 引用校验器把自己举的例子当成真引用 | 引用正则**必须匹配行首**（允许前置注释符），否则会匹配到描述格式的散文 |
| 7 | 派发 `KeyboardEvent` 到 `document` 触发不了全局快捷键 | 监听在 `window` 上，而 `document.dispatchEvent` **不冒泡到 window**。测试要 `window.dispatchEvent` |
| 8 | 浏览器测试"清理不彻底"残留 1 条 | 测试有**两条创建路径**（API 直建 / UI 极速录入），后者没记进 `created` 数组。清理必须**再按标题前缀扫一遍并真的删除**，只扫描报警是不够的 |

### 12.3 一次语义错误（已修，重要）

第一版实现把"已完成 或 已过期"统一用于两种 `tone`，导致
**超期未完成的 `todo` 也被计入进度分子**——拖着不做反而让进度变高。

拆分后（§2.2）：`is_overdue()` 回答"时间过没过"，`counts_as_progress()` 回答"算不算达成"。

**端到端证据**：点击一条超期 `todo` 前后——

| 时刻 | done | overdue | numerator | ratio |
|---|---:|---:|---:|---:|
| 点击前 | 1 | 2 | **2** | 33.3% |
| 点击后 | 2 | 1 | **3** | 50% |

它在点击前**没有**计入分子。若沿用作废的第一版，它早就被算进去了，勾选不会有任何变化。

### 12.4 一次排序缺陷（已修）

「未安排」组的两条事项排序键**完全相同**（都是 `(0, 时间)`），
而 `sorted()` 是**稳定排序**——于是保留查询返回顺序（MySQL 按主键升序），
结果是**刚记下的事沉到列表下面**，用户会怀疑"到底记上了没"。

用户实测发现后定案：**组内最新的排最前**。实现是给排序键加次级键 `-id`
（id 自增，等价于创建时间倒序）。固化为
`calendar_crud_cases.py::test_unscheduled_group_newest_first`。

> 这条的教训：**排序键不完整时，`sorted()` 不会报错，只会给出一个"看起来随机"的顺序**。
> 凡是"同 key 时谁在前"没被明确决定的排序，都值得补一个明确的次级键。

### 12.5 一次漏掉的过滤（已修）

加「已作废」时，`pending_events()` 加了 `archived_at IS NULL`，
但 **`week_progress()` 漏了**——它不调用 `pending_events()`（周窗是另一套口径，
按 `event_date` 范围查，不按"未完成"查），所以两个函数的过滤是**各自独立**的。

后果：作废一条事项后，周进度的分母**不变**，完成率**静默地**不动。
没有任何报错，数字看起来也"正常"——只是它不是你要求的语义。

**是测试先抓到的**：那条断言写着"作废后分母减 1"，第一次跑就红了。

> 教训：**当一个过滤条件需要施加到 N 个查询上时，"集中在一处"只在它们共用入口时成立。**
> `pending_events()` 的集中化确实让待做清单只改了一行，但周进度是另一条路径——
> 它需要自己的断言。固化为
> `calendar_crud_cases.py::test_archived_does_not_count_toward_week_progress`。
