### 2.8 修复 H1 — 笔记阅读区被 TradeSim 的全局样式染白

**这是一个用户可见的真实 bug**，审计里编号 H1。

**成因**：`TradeSimSimulator.vue:8` 与 `TradeSimDetail.vue:8` 在 **import 阶段全局引入** `github-markdown-css/github-markdown-light.css`。该文件给 `.markdown-body` 设了 `background-color:#ffffff; color:#1f2328`，并给标题、链接、代码块、引用、表格配了一整套浅色。而门户的笔记阅读器（`Notes.vue:1521`）**恰好就用了 `markdown-body` 类**。

**症状**：**只要本次会话访问过任意 TradeSim 页面，再回到笔记页，阅读区就整块变白、标题几乎看不见。**

**修法**：在 `Notes.vue` 的 scoped 样式里把阅读区钉回门户暗色主题（容器 `background: transparent; color: var(--text)`，并覆盖标题/链接/代码/引用/表格/分隔线的颜色）。

**为什么这样能生效**：`Notes.vue` 的样式块是 `scoped`，选择器会被编译成 `.reader-document.markdown-body[data-v-xxx]`，**特异性 (0,3,0) 高于全局 `.markdown-body` 的 (0,1,0)**，因此与加载顺序无关，稳定压过泄漏。已在产物中确认编译结果：

```
.reader-document.markdown-body[data-v-b86f7c47]{color:var(--text);background:0 0}
```

**这是"门户侧自保"，不是根治**。彻底的做法（`docs/4` §12.1）是把 TradeSim 那两个全局 import 改成只在 `.tradesim-layout` 命名空间内生效——那属于 TradeSim 侧改动。**该根治已于同日完成，见 §2.9**；本页这段随之收窄为纯兜底。

### 2.11 批次 2.4：DOM / RAF 泄漏（`App.vue` + `useScrollReveal`）

`docs/4` 的动效审计判定这两处有清理缺陷。逐行核实后**两处都成立**，都已修。

**① `App.vue` 的 Lenis RAF 循环永不停止**

原实现是：循环体里 `lenis?.raf(time)` 之后**无条件** `requestAnimationFrame(raf)`，而那个返回值被丢弃；`onBeforeUnmount` 只做 `lenis?.destroy()`。于是 `destroy()` 之后循环仍在空转。真实影响：

- 组件卸载后循环继续——`App` 是根组件，正常运行不会卸载，所以生产态影响有限；
- **开发态每次 HMR 都会再叠一层循环，旧的永远不停**——这是实打实的 CPU 泄漏，也解释了为什么长时间开发时机器会越来越热。

修法：保存 RAF 句柄；循环体内加 `if (!lenis) return` 守卫；卸载时先 `cancelAnimationFrame(rafId)`，再 `destroy()`，最后把 `lenis` 置 `null`（让守卫对"正在进行中的那一帧"也生效）。

**② `useScrollReveal()` 的 IntersectionObserver 从不 disconnect**

`Dashboard.vue:776` 原本是裸调用 `useScrollReveal()`，**返回值被丢弃**，而 `onBeforeUnmount` 只清掉了 Canvas 的 RAF。于是观察器在组件卸载后仍然存活，**一直持有那些 `.reveal-item` DOM 节点**（节点无法回收），并继续对已脱离文档的元素写 class。

修法：`Dashboard.vue` 持有 `revealObserver`，在 `onBeforeUnmount` 里 `disconnect()` 后置 `null`。

**为什么没把自动清理写进组合式函数**：`onScopeDispose()` 在这里**不生效**——`useScrollReveal()` 是在 `onMounted` 回调里调用的，那时已无活动 effect scope，Vue 只会打印 "no active effect scope" 警告。一个"看起来已经清理好、实则静默失效"的实现比不做清理更糟，所以清理责任显式交给调用方，并把契约写进 `useScrollReveal.ts` 的文档注释。注释里同时记下另一个坑：该函数在**调用瞬间**就抓取 `.reveal-item`，若在 `setup()` 里直接调用会一个都抓不到（滚动揭示静默失效），**必须在 `onMounted` 或之后调用**。

**验证**：`vue-tsc` exit 0、`npm run build` exit 0；改动点在源码中逐行核对——`App.vue` 的 `rafId` 取得／守卫／取消／置空，`Dashboard.vue` 的 `revealObserver` 声明（`584`）／赋值（`776`）／断开（`798-799`）。

**本次改动不影响滚动揭示的触发时机**（调用点、调用时机、观察目标都没变，只是补上了卸载时的断开），因此首页入场动画不存在"因本次改动而失效"的路径。但它属于动效，仍请你在页面上扫一眼确认无碍。

### 2.12 分钟级（1min/5min）行情：接入降级链 + 补上区间裁剪

`docs/5` §9 原本把这项记成"今晚遗留"，但核实后它**不是可选项而是真实缺陷**，已修。

**先确认它不是死代码**：`TradeSimSimulator.vue:466` 有绑定 `form.data_frequency` 的 `el-select`，`schemas/simulate.py:8` 也把 `daily, 5min, 1min` 写进了字段描述。也就是说**用户在界面上选 1min/5min 时走的就是这条分支**——而它原先只有东财一条路径（代码里还留着"注意：分钟级目前只有东财一条路径，尚未接入降级链"的注释），东财的 K 线主机在本机又恰好不可用（见 §3 的 H2 诊断）。结论：**这个功能此前 100% 必然失败**。

**改法**：新增 `DataFetcher._fetch_intraday()`，与日线同构的降级链 **东财 → 新浪**（`stock_zh_a_hist_min_em` → `stock_zh_a_minute`）。

**关键的一步不是降级链，而是区间裁剪。** 实测新浪分钟接口的特性：

| 参数 | 返回 | 覆盖区间 |
|---|---|---|
| `period="5"` | 1970 行 | `2026-07-23 14:55` → `2026-09-18 15:00` |
| `period="1"` | 1970 行 | `2026-09-08 13:53` → `2026-09-18 15:00` |

**它不接受日期区间**，只给最近约 1970 根的固定窗口。如果直接接上，用户请求 2024 年的区间就会拿到 2026 年的数据，然后**"成功"跑出一份看起来完全正常、实际整体错位的回测**——这比直接报错危险得多，因为它不会引起任何怀疑。所以新增 `_clip_to_range()` 在本地按 `[start_date, end_date]` 裁剪，并且：**裁剪后为空就继续降级，全部源都空则返回 `None`**，由上层给出可读的 400。

顺带修掉一处 `_normalize()` 的隐患：原实现把 `_COLUMN_ALIASES` 里命中的列**全部**改名，而东财分钟源同时返回 `时间`、部分源也带 `日期`，一旦两者并存改名就会造出两个同名列并让 `pl.from_pandas` 失败。现改为"**不覆盖已存在的目标列**"，并给别名表补上 `day`、`时间`。

**实测证据**（全部在本机真实执行）：

| 场景 | 结果 |
|---|---|
| `5min` 600585 `2026-09-01 ~ 2026-09-18` | **HTTP 200**，命中新浪，裁剪后 **672** 个净值点，成交 32 条，首末日期正好是请求区间 |
| `1min` 600585 `2026-09-10 ~ 2026-09-18` | 命中新浪，裁剪后 **1666** 行 |
| `5min` 请求 `2024-01-01 ~ 2024-06-30`（窗口外） | 新浪返回 1970 行 → 裁剪后 **0** 行 → 拒绝，**HTTP 400「无法获取代码 600585 在指定日期范围内的数据」**，未静默给错数据 |
| `daily` 回归 `2025-01-01 ~ 2025-06-30` | **117** 行，命中东财，未受本次改动影响 |
| 非法策略名 | HTTP **400**（不是 503），确认 `docs/4` 要求的"策略名校验先于行情拉取"已生效 |
| 6 条已存记录 `detail/1..6` | 全部 200，净值点 242 / 2676 / 2652 / 2431 / 2431 / 2431，与改动前一致 |
| 后端门禁 | 策略用例 **8/8 PASS**；`import main` OK，表 `['bills','calendar_events','simulation_records','tags']` |

**已知且有意保留的限制**：`_normalize()` 只取时间戳前 10 位，所以分钟级数据的日期标签**只有日期没有时分**（同一天的 48 根 5 分钟 K 线共用同一个日期字符串）。**这与原先东财路径的行为完全一致**，属于既有口径而非本次引入；若要改成带时分的标签，会改变已落库与图表显示的格式，属"看得见的变化"，需你决定，故归入方式②。

### 2.14 批次 3.4（部分）：补 `monthly_summary` 契约、补齐 `models` 门面；并纠正 `docs/4` 的又一条错误建议

**① `monthly_summary` 补 `response_model`。** 该路由此前**没有** `response_model`，于是走 FastAPI 的 `jsonable_encoder`，而它对 `Decimal` 的处理是"**整数值返回 int、带小数返回 float**"——同一个字段的类型会摇摆。实测 2026-06 就同时出现了两种：

```

```


| `utils/format.ts` | 全仓只有 `fmt(n) { return n.toFixed(2) }` 一处，加 Dashboard 模板里一处 `toLocaleString('zh-CN')` | **不做**。为 1 个单行函数建一个模块没有收益 |
| `utils/markdown.ts` | Notes.vue 的手写解析器与 TradeSim 的 `marked`+`DOMPurify` 是**两套不同实现**，不是重复 | **不做**（风险已记在 §2.11，但它不属于"去重"） |
| `PortalHeader.vue` / `BaseModal.vue` / `ErrorBanner.vue` | 属于**模板与样式**抽取，会直接影响你看得到的界面 | **暂不做**，留给需要你眼睛确认的那一批 |

**顺手抓到的真 bug（这是本批最大的收获）**

`Bills.vue` 里新建账单的默认日期用的是 `new Date().toISOString().slice(0, 10)`。`toISOString()`
永远返回 **UTC**；在东八区，当地 00:00–07:59 对应的 UTC 还在前一天 —— 这 **8 小时**里"今天"会被算成
"昨天"。表单里有两处：`emptyForm()` 的默认值，以及切换收支类型后的重置。

这不是理论推断，**我跑验证时正好撞进窗口里**：

```
当前本地时间: Sun Sep 20 2026 06:12:39 GMT+0800 (中国标准时间)
todayKey()                = 2026-09-20   <- 正确
toISOString().slice(0,10) = 2026-09-19   <- 旧代码，差一天
```

也就是说那个时刻打开"新建账单"，日期会默认成昨天。修完之后用
**`node --experimental-strip-types` 直接执行真实的 `frontend/src/utils/date.ts`** 做验证
（Node 22.17 支持该开关，所以验的就是发布出去的那份代码，不是我另写的等价逻辑），**8 PASS / 0 FAIL**：

| 用例 | 期望 | 结果 |
|---|---|---|
| `dateToKey(2026-09-21 本地)` | `2026-09-21` | PASS |
| 补零：`dateToKey(2026-01-05)` | `2026-01-05` | PASS |
| `padDatePart(7)` | `07` | PASS |
| 闰年：`dateToKey(2024-02-29)` | `2024-02-29` | PASS |
| 当地 00:30 / 03:30 / 07:59（UTC 仍是前一天） | `2026-09-21` | 3 条全 PASS |
| 边界：当地 08:00 | `2026-09-21` | PASS |

（顺带记下这个验证手法：`TZ=Asia/Shanghai node --experimental-strip-types <file>` 能在**没有
vitest、没有任何前端测试设施**的前提下直接测 TS 纯函数。以后写前端纯函数可以沿用。）

**改动**：新增 `frontend/src/utils/date.ts`（`padDatePart` / `dateToKey` / `todayKey`，一律走本地
时区，文件头注释里带上面那张 UTC 对照表当反例）；`Dashboard.vue` 删掉本地重复的
`padDatePart`/`dateToKey` 改为导入（7 个调用点行为**完全不变**，它本来就是本地时区写法）；
`Bills.vue` 两处改用 `todayKey()`。

**门禁**：`vue-tsc --noEmit` exit 0；`npm run build` exit 0（1.11s）。全仓 `toISOString` 只剩
`date.ts` 注释里的 4 处引用（作为反例保留），**代码里已清零**。

### 2.21 批次 3.3：解除背景组件对使用页面的反向耦合（`:global` 逃逸）

**问题**：`StarfieldBackground.vue` 声明的是 `<style scoped>`，但里面有一个 `:global(.starry-workspace)` 块
—— 一个**背景组件**用 `:global()` 逃出作用域，反向给"使用它的页面"定义布局和整套设计变量。这正是你反馈的
"背景/动效复用与共享混乱"的一个样本：它看起来是可以挂到任何页面的共享背景层，实际上一旦挂到别的页面，
就会顺手改掉那个页面的配色。

**先实测，再决定怎么改**：

| 事实 | 证据 |
|---|---|
| `.starry-workspace` 全仓只被 `Bills.vue:282` 使用 | `starry-workspace` 全仓命中 2 处，其一是定义处 |
| 该块里 9 个变量与 `main.css` 的 `:root`（第 5–15 行）**取值逐条相同** | 逐条比对：`--primary:#7c3aed`、`--primary-light:#a78bfa`、`--primary-dark:#5b21b6`、`--surface:#0f0f14`、`--surface-light:#1a1a24`、`--surface-card:#1e1e2a`、`--text:#e2e8f0`、`--text-muted:#94a3b8`、`--border:#2e2e3a` |
| 真正生效的只有 3 条 | `position: relative`、`isolation: isolate`、`background: rgba(7,8,22,0.78)` |

那 9 个变量因此是**冗余副本**，删掉不会改变任何计算值。

**改动**：`Bills.vue` 自己的 scoped 样式里补上那 3 条声明（附注释说明它们为什么在这里）；
`StarfieldBackground.vue` 里整个 `:global` 块删除，并留注释说明为什么不能再加回来。

**等价性验证（不靠眼睛，用构建产物逐条比对）**

改前的产物 CSS —— 注意选择器**没有** `[data-v-*]`，这正是逃逸的证据：

```css
.starry-workspace{isolation:isolate;--primary:#7c3aed;--primary-light:#a78bfa;
--primary-dark:#5b21b6;--surface:#0f0f14;--surface-light:#1a1a24;--surface-card:#1e1e2a;
--text:#e2e8f0;--text-muted:#94a3b8;--border:#2e2e3a;background:#070816c7;position:relative}
```

改后：

```css
.starry-workspace[data-v-6f8cdec5]{isolation:isolate;background:#070816c7;position:relative}
```

| 检查项 | 结果 |
|---|---|
| 声明数 | 12 → **3** |
| 删掉的 | 正好是那 9 个变量，**无一例外** |
| 新增的 | **0 条** |
| 两边共有的 3 条 | `background:#070816c7`、`isolation:isolate`、`position:relative` **逐条一致** |
| 9 个变量的取值 | 每个在产物里的出现次数**恰好减 1**（去掉的是重复副本），`:root` 那份仍在 |
| 未带属性选择器的 `.starry-workspace` 规则 | **0 条**（逃逸已消除） |

元素上算出来的值完全相同，而它对其它元素的影响则从"可能"变成了"没有"。

**门禁**：`vue-tsc --noEmit` exit 0；`npm run build` exit 0（1.09s）。

**附带记下一个潜在陷阱**：`:root` 与 `.theme-light` 都定义了这套变量（后者改的是
`--surface`/`--surface-light`/`--surface-card`/`--text`/`--text-muted`/`--border`，`--primary*` 不变）。
原先 `.starry-workspace` 上的硬编码暗色值**优先级高于** `html.theme-light` —— 也就是说，**如果哪天真把
浅色主题接回来，记账页仍会是暗的**，而原因藏在一个背景组件里。现在这个陷阱随 `:global` 块一起消失了。

### 2.23 后端死代码维度：用 AST 扫描（结论：干净），以及"我连续两次产出假清报告"的教训

前端做过批次 1.2/1.3 的死代码清扫，**后端此前只清过一处**（批次 1.5 的 `db.refresh`）。这一维度不能靠 grep
（分不清"真的没用到"和"只出现在字符串/注释里"），所以用零依赖的 Python `ast` 写了个扫描器，只读、不改文件，
查四类：① 未使用的 import；② 定义了但全仓从未按名引用的模块级符号；③ 孤儿模块；④ 函数/方法体重复
（归一化 AST 哈希）。

**最终结论（基于 42 个 .py 文件的真实解析、108 份全仓文本作参照）**：

| 检查 | 结果 |
|---|---|
| 未使用的 import | **0 条**（`from __future__ import annotations` × 7 是假阳性：它没有绑定名） |
| 被孤立的模块级定义 | **0 条**（首轮报出的 6 条全是 FastAPI 路由处理函数，靠装饰器注册，不靠名字引用） |
| 孤儿模块 | **0 条**（详见下面的第三次假阳性） |
| 重复的函数体（≥6 行） | **0 条** |

也就是说：**后端没有死代码** —— 这是一条有证据支撑的结论，不是"没查"。

> ⚠ **本节要记的不只是结论，还有我拿到这个结论的过程：我的前两版扫描器都给出了"全部干净"的报告，而两次都是假的。**
>
> | 版本 | 报出的结论 | 实际的错 |
> |---|---|---|
> | 第一版 | 四类全是"无" | 我把根路径拼成了 `Knowle` + `dgeMap`，而真实目录名是 **`KnowdegeMap`**（项目名本身就这么拼）。`os.walk` 对不存在的目录**不报错**、直接返回空 → 报告末尾那句 **`扫描 0 个 .py 文件`** 就是铁证，四条"无"全部无意义 |
> | 第二版 | 孤儿模块 **27 个** | 模块名被我拼成了 `app.app.crud.bill`（rel 路径已含 `app/`，我又加了一次前缀），于是匹配永远为空 → 27 个全是假阳性。另两类"无"是真的 |
> | 第三版 | 孤儿模块 3 个 | 仍未正确：`from app.tradesim.api.v1 import ai` 里 **`ai` 是子模块名**，而我只登记了包名 `app.tradesim.api.v1`。三处 `api/v1/*.py` 全是假阳性（`router.py:3` 明确 import 了它们） |
>
> 教训很直接：**"没有发现问题"的报告，价值取决于能否证明"扫描器真的看过、并且有能力发现问题"。**
> 因此第三版加了**自检**——断言已知被引用的模块（`app.database`、`app.crud.bill`）必须被判为"已引用"、
> 断言不存在的模块必须不被判为已引用，并把"实际扫到多少文件、多少参照文本"打进报告。第一版那两行如果早点
> `assert` 一下，就不会写出一份假结论。**以后凡是要下"审计没发现问题"这类结论，都要先能证明扫描器不是空转。**

扫描器本身是临时脚本（放在 `%TEMP%`），没有进仓库——它是一次性审计工具。关键结论另用 grep 复核过：
6 个"未引用"函数逐个确认是 `@router.get/post` 装饰器注册的活端点，与 §8 里这些端点返回 200 的实测一致。

### 2.24 接口契约维度（反向）：后端暴露但前端从不调用的接口

前面几节验的是**前端→后端**方向（15 个调用点逐条重放，全部 200/422/404 符合预期）。反向从来没查过：
**后端注册的路由里，哪些没有任何前端调用**。这属于"接口契约与文档一致性"维度缺的一块。

**做法**：直接从 FastAPI 的 `app` 对象上枚举**实际注册的路由**（不信文档），再用 grep 在 `frontend/src/`
里逐个对账。实测后端共 **27 条** `(method, path)`，其中 4 条是 FastAPI 自带的（`/docs`、`/docs/oauth2-redirect`、
`/openapi.json`、`/redoc`），应用路由 **23 条**。

**结论：前端确实从未调用其中 5 条。**

| 未接入 UI 的接口 | 说明 |
|---|---|
| `GET /api/bills/{bill_id}` | 对当前 UI 是**冗余**的：列表响应已经带着模态框需要的全部字段 |
| `PATCH /api/calendar-events/{event_id}` | **后端支持改日程，界面不支持** |
| `POST /api/tags/` | 无标签管理界面 |
| `PATCH /api/tags/{tag_id}` | 同上 |
| `DELETE /api/tags/{tag_id}` | 同上 |

另有 `GET /api/health` 也不被前端调用，但这是**设计如此**（面向运维而非用户），AGENTS.md 的接口清单里
已单独列出。顺带记一条 `docs/4` 早已指出、至今仍成立的事实：`/api/health` **恒定返回
`{"status":"ok"}`、不探测 MySQL/Mongo**，所以它只能当存活信号、**不能当就绪探针**——数据库挂了它照样 200。

**这不是死代码**，我没有改任何一行：一套完整的 REST 面本身是合理的。但这三个后果你值得知道：

1. **标签管理完全没有界面**。标签只能靠 `reseed_categories` 脚本或 SQL 改；增删改三个接口是"给一个还不
   存在的界面预留的"。你此前选了"保留标签体系现状"，所以这与你的意图一致，只是值得明确写下来。
2. **日程只能新建和删除，不能改**（后端接口是现成的）。今天发现写错了日期，只能删掉重建——这是唯一一个
   "后端已就绪、只差一个界面"的功能缺口，也是本次审计里最像"值得做的新功能"的一条（属新增功能，故不在
   本轮"不新增功能"的范围里）。
3. `GET /api/bills/{id}` 如果确认永远不用，**可以考虑删掉**以减少表面积；但它也可能被将来的外部脚本用，
   所以我按方式②只记录、不删。

### 2.29 ⭐ 新发现（不在 `docs/4` 的 26 条内）：`grid_step_pct` 的单位在迁移时分叉了

追查上面那条"指标对不上"时，发现了一个**用户可见**的问题，属于"接口契约一致性"这一维度。

**引擎的契约是"百分数"**：`grid_trade.py:113` 的 `_percent_to_ratio()` 写着 `"""Convert API/user
percent input to calculation ratio. 5 means 5%."""`，`:101`/`:117` 的报错文案也是"例如 5 表示 5%"；
schema 的示例是 `"grid_step_pct": 5.0`。**这是正确的当前契约。**

**但已存的 6 条记录用的全是旧单位（小数）**——实测每条都是 `0.05`，没有一条是百分数：

| id | grid_type | grid_step_pct | 全部参数 |
|---|---|---|---|
| 1 | （无） | **0.05** | lower 15 / upper 25 / funds 10000 / base 0.3 |
| 2 | （无） | **0.05** | lower 15 / upper 35 / funds 10000 / base 0.3 |
| 3 | （无） | **0.05** | lower 15 / upper 25 / funds 10000 / base 0.5 |
| 4 | arithmetic | **0.05** | grid_count 20 / lower 10 / upper 50 / volume 模式 |
| 5 | arithmetic | **0.05** | grid_count 20 / lower 10 / upper 50 / **funds_per_grid 100** |
| 6 | geometric | **0.05** | grid_count 20 / lower 10 / upper 50 |

**对照实验**（同一份数据、同一区间，只改这一个参数的单位，直接调引擎）：

| `grid_step_pct` | 网格节点数 | 完成周期 | 盈利周期 | `win_rate` | `total_trades` |
|---|---|---|---|---|---|
| **0.05**（旧单位当百分数用） | **1023** | 43 | **0** | **0.0** | 86 |
| 0.5 | 103 | 46 | 46 | 1.0 | 92 |
| **5**（文档语义 = 5%） | **11** | 13 | 13 | **1.0** | 26 |
| 10 | 6 | 6 | 6 | 1.0 | 12 |

两件事因此被算清：

1. **`win_rate = 0` 不是引擎的 bug，而是它对错误单位参数的正确反应。** `0.05` 被当成 0.05% →
   `15 × 1.0005^n = 25` → n ≈ 1022，**正好 1023 个节点**；此时每格步长约 0.0075 元/股，
   **小于双边滑点 0.02 元/股**，所以每个完成周期必然亏 0.02 元/股。算术闭合：
   `43 周期 × 400 股 × 0.02 = 344.0`，与 `realized_grid_profit = -344.05` 吻合。
   换成文档语义的 `5` 后，节点数 11、13 个周期全部盈利、`win_rate = 1.0`——**引擎是对的**。

2. **详情页的网格线用了旧单位，于是对新记录会画错。**
   `TradeSimDetail.vue:182` 是 `currentGrid *= (1 + form.strategy_params.grid_step_pct)`，
   **漏了 `/100`**；而模拟器里两处都有（`TradeSimSimulator.vue:55` 与 `:123`）。
   这段计算结果并非死代码——它被 `:239` 的价格序列消费：`markLine: { … data: dynamicGrids }`，
   所以网格线是**真的画在价格图上的**。后果：
   - 对 6 条老记录（`0.05`）：`1 + 0.05` 正好是 5%，**画出来是对的**（因此这个问题至今没被发现）；
   - 对**任何新存下的记录**（`5`）：`1 + 5` = 600%，`while` 循环第一轮就越过 `upper_bound`，

> 🔴 **更正（本轮用另一种量具独立复核后，详见 §2.39）**：本节上面那张表里的**节点数与我记的周期数都是错的**。

> 本轮另从 HTTP 响应侧（`execution_records`）独立确认了亏损机制：`slippage_cost = volume × 0.01`

> **推荐方案 A 的结论不变，且更有把握**：A 让那 4 条 geometric 记录**保持 115 条不变** ✓。

| 方案 | 做法 | 后果 |
|---|---|---|
| A（推荐） | 详情页按 `step >= 1 ? step/100 : step` 归一 | 老记录与新记录**同时**正确；代价是这条启发式规则要在注释里写明为什么 |

### 2.38 新维度：数据库 schema 漂移与索引审计（只读）＋ 把 H3 的收益量化成一个数字

前面 37 节审计的都是**代码和文档**，唯独没审过**数据库结构本身**。这一维度值得单独做，
因为 `docs/3` 明确记着"schema 由 `Base.metadata.create_all()` 产生"，而 **`create_all()` 从不 ALTER 已存在的表**
—— 那么"模型改了、线上库没跟上"这类漂移，**在代码里看不出来、在两套测试里也看不出来**
（测试跑的是内存 SQLite，每次从模型现建）。只有把两边摆在一起比才会暴露。

#### 做法（全程只读 + 一次性临时库，用完即删并复验）

① 用 `information_schema` 逐表逐列比对模型与线上；② 另建一个**临时库** `knowledgemap_schema_probe`，
在里面用 `Base.metadata.create_all()` 现建，再 `SHOW CREATE TABLE` **逐字 diff** 两边；③ 删掉临时库并**复测线上行数**。

> **安全证明**：探测前后线上行数完全一致 —— `bills 29 → 29`、`tags 39 → 39`、`calendar_events 0 → 0`、
> `simulation_records 6 → 6` ✓；`SHOW DATABASES` 复验**没有遗留任何 `knowledgemap*` 临时库** ✓；
> 临时脚本与产物已全部删除（`git status` 只剩原本就未跟踪的 `tp.md`）✓。

#### 结论一：**没有致命漂移** ✓

- 表集合完全一致：模型 4 张 ↔ 线上 4 张，**没有"只在模型、线上没有"的表**，也没有遗留表 ✓
- **不存在"模型有某列、线上库没有"的情况**（0 处）—— 这是会直接导致运行时 `Unknown column` 的那一类，没有 ✓
- `bills` / `tags` / `calendar_events` **三张表结构完全一致**：现建与线上的差异**只有 `COMMENT`、
  `CHARACTER SET/COLLATE` 声明、`AUTO_INCREMENT` 这类装饰**，列的类型与可空性逐列相同 ✓

#### 结论二：⭐ 只有 `simulation_records` 一张表有**真结构差异**，而且它**不是 `create_all()` 建的**

| 列 | `create_all()` 现建 | 线上库 |
|---|---|---|
| `user_id` | `bigint DEFAULT '0'`（**可空**） | `bigint **NOT NULL** DEFAULT '0'` |
| `data_frequency` | `varchar(20) DEFAULT 'daily'`（**可空**） | `varchar(20) **NOT NULL** DEFAULT 'daily'` |
| `annualized_return` | `decimal(10,4) DEFAULT (0.0000)`（**可空**） | `decimal(10,4) **NOT NULL** DEFAULT '0.0000'` |
| `created_at` | `timestamp **NULL** DEFAULT CURRENT_TIMESTAMP` | `timestamp **NOT NULL** DEFAULT CURRENT_TIMESTAMP` |

另外索引名不同（现建 `ix_simulation_records_*` / 线上 `idx_simulation_records_*`）、多列中文注释不同
（例如库端 `user_id` 是'当前单用户模式'，模型里写的是'目前暂无多用户,留空或置0'）。

**来源被实测定死了**：`表结构/tradesim.sql` 里这些列的定义与线上**逐字一致**（含 `NOT NULL` 与同款注释与 `idx_` 索引名）
⇒ **线上这张表是这个 DDL 文件建的**，模型与 DDL 是**两份互相独立、且在 4 列上互相矛盾**的描述。
文件本身是干净的：有说明头、`CREATE TABLE IF NOT EXISTS`、`USE knowledgemap;`、**0 处 `DROP`**（与 H5 那个
`knowledgemap.sql` 不同）。⚠ 但也正因为是 `IF NOT EXISTS`，**它同样修不了漂移** —— 表已存在时它什么都不做。

**后果（诚实版）**：这 4 列在线上都带 `DEFAULT`，而应用从不显式写 `NULL`
（`SimulationRecord` 里没有 Python 侧默认值，SQLAlchemy 直接省略该列、由 `server_default` 兜住）
⇒ **今天没有任何实际影响**。真正的隐患是**方向**：**新装一台机器时建出来的表比这台机器"松"**
（`created_at` 甚至允许显式写入 `NULL` 而不报错）。也就是说 —— **那 4 个 `NOT NULL` 约束只存在于这台机器上。**

#### 结论三：顺带解释了一个**看起来像不一致**的地方（不是缺陷）

数据库里 `record_type` / `reimbursement_status` / `tags.type` / `calendar_events.tone` 存的是**枚举的"名字"**
（`expense`/`income`、`na`/`pending`/`done`、`category`/…），而 API 与文档说的是**中文值**（`支出`/`收入`）。
这是 SQLAlchemy `Enum` 的默认行为（存成员名，除非用 `values_callable`），**不是 bug**。
⚠ 顺便它也解释了我自己第一版量具的假象：`str(Enum)` 会渲染成 `VARCHAR(7)` —— 那个 `7` 正是最长枚举名
`'expense'` 的长度，我却把它当成了"类型不一致"。

#### 结论四：索引审计 —— 唯一缺口是 `bills` 的排序列

| `calendar_events` | `event_date` 有索引 ✓ |

### 2.45 第七轮独立复核：**维度五「死代码与冗余资产」**——结论：**没有死代码**，只有"导出范围偏宽"和几处"有意保留" ⭐

方法（全部新写，不复用旧结论）：后端用 **AST** 收集"函数/方法定义"与"全仓引用"，前端**只扫 `<script>` 块** +

#### ① 后端：81 个函数/方法中**零引用者 = 0**（唯一命中是量具假阳性）
