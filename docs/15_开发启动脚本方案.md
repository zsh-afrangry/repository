## 2. 现状核实：一开始的认知需要纠正

用户最初设想"需要一份表结构 SQL 来初始化表"。**实际上不需要**——
先把现状核准，避免方案建在错误前提上：

| 层级 | 谁负责 | 现状 |
|---|---|---|
| MySQL 服务 | 系统/用户 | ✅ 已有 |
| **数据库 `knowledgemap`** | **没人** | ❌ **这就是唯一缺口** |
| 表 | `main.py` 的 `Base.metadata.create_all()` | ✅ 自动 |
| 字典/种子数据 | `main.py` 的 `seed_default_tags()` / `seed_notes()` | ✅ 自动 |

`create_all()` **只能建表，不能建库**。库不存在时 SQLAlchemy 抛
`Unknown database 'knowledgemap'`，而这个错发生在 lifespan 里，**服务根本起不来**。
所以启动脚本要先保证库存在——这是它要补的唯一硬缺口。

### 2.1 `backend/sql/knowledgemap.sql` 不是初始化脚本

它已存在，但用途是**核对结构漂移**，**不是**初始化。理由（文件头也写着）：

> ⚠️ 含 `DROP TABLE IF EXISTS`，**不要**直接对生产库执行

对已有数据的库执行它会**清空真实数据**。所以启动流程**绝不执行这个文件**。

### 2.2 字典表与种子数据

用户的直觉是对的——本项目确实有"必须先有数据，业务才能跑"的表：

| 表 | 性质 | 没有它会怎样 | 谁补齐 | 判定方式 |
|---|---|---|---|---|
| `tags` | **字典表** | 记账选不了分类/支付方式 | `seed_default_tags()` | **表是否为空** |
| `notes_topics` | 种子内容 | Notes 页面空白 | `seed_notes()` | **版本标记行**（`NotesSeed`） |
| `notes_seed_versions` | 版本标记 | 无法判断是否灌过，会重复灌 | `seed_notes()` | — |

**⚠️ 两种判定方式不统一，各有隐患**：`tags` 用"表为空"判断，
所以**把 tags 全删了之后重启后端，39 个默认标签会又冒出来**；
而 notes 用版本标记，不会。这是既有实现的差异，**本次不修改**（超出范围），
但值得知道。

**结论**：启动脚本**不需要**自己灌种子数据——`main.py` 已经做了。
脚本只保证"库存在"，然后交给 `main.py`。

## 3. 设计

### 3.1 三层结构

```
┌─ 第 1 层：平台启动脚本 ─────────────────────┐
│  dev-start.ps1（Win11）  dev-start.sh（Ubuntu）│
│  职责：环境检查、端口决定、起进程、收摊        │
└────────────────────┬───────────────────────┘
                     ↓
┌─ 第 2 层：数据库/服务自检（跨平台共用）──────┐
│  backend/scripts/ensure_database.py          │
│  职责：建库（唯一缺口）+ 报告表/种子/Mongo     │
│  ——纯 Python，两平台共用同一份                  │
└────────────────────┬───────────────────────┘
                     ↓
┌─ 第 3 层：建表 + 种子数据（已存在，不动）────┐
│  backend/main.py 的 lifespan                 │
└─────────────────────────────────────────────┘
```

**为什么第 2 层要独立成 Python 脚本**（而不是塞进平台脚本里）：

| 理由 | 说明 |
|---|---|
| 两平台共用一份 | 否则 PowerShell 写一遍、Bash 再写一遍，两边迟早不一致（`docs/14` §12.3 的教训） |
| 可单独测试 | 能对它写隔离用例，不必真起服务 |
| 可手工运行 | 排障时直接 `python backend/scripts/ensure_database.py` |
| 复用既有约定 | 项目已有 `backend/scripts/` 放辅助脚本、脚本头部带 `对应文档：` 引用的约定 |

### 3.2 端口由启动脚本统一决定（决策 1）

**这是本方案最重要的设计。** 端口只在一个地方决定，然后注入两个进程：

```
后端  <- KM_BACKEND_PORT   （main.py 读它；默认 8010）
前端  <- KM_API_TARGET     （vite.config.ts 读它，作为代理目标）
```

**为什么不能"让前端自己去读后端端口"**：

```
浏览器 → Vite dev server (:3000) → 代理 → 后端 (:8010)
              ↑ 代理发生在这里（Node 进程内部），不是浏览器里
```

代理发生在 **Node 进程内部**，所以"读后端端口"只能发生在 **Vite 启动那一刻**，
方式只能是环境变量。若两边各自决定端口，一旦不一致：**页面能打开，
但所有接口 404**——这种故障很难定位（看起来像后端挂了）。

**好消息**：`frontend/vite.config.ts:6` **已经支持** `KM_API_TARGET`：

```ts
const apiTarget = process.env.KM_API_TARGET ?? 'http://localhost:8010'
```

所以本需求**不需要改任何前端代码**。

### 3.3 MongoDB 只检查、只报告（决策 2）

**用户的 MongoDB 现状**（2026-10-08 实测）：

| 项 | 值 |
|---|---|
| 版本 | MongoDB **8.2.1**（`C:\Program Files\MongoDB\Server\8.2\`） |
| 运行方式 | **Windows 服务**，名称 `MongoDB` |
| 状态 / 启动类型 | `Running` / **`Automatic`（开机自启）** |
| 监听 | `127.0.0.1:27017` ✅ |
| Compass | 1.49.14 —— **只是 GUI 客户端，不是数据库本体** |
| `mongosh` | **未安装** |
| `pymongo` | 4.15.5（`desheng` 环境内） |

**两个结论**：

1. **Compass 不是数据库。** 数据库本体是那个 `MongoDB` 服务。这值得澄清，
   因为很容易以为装了 Compass 就有数据库了。
2. **脚本不启停 Mongo。** 它是开机自启的服务，脚本若去 `Start-Service`，
   会出现"服务被停过 → 脚本偷偷启动 → 你不知道为什么它之前是停的"。
   开发脚本应该让你**清楚**环境状态，而不是替你改。

**因为没装 `mongosh`**，检查用 `pymongo` 做（与后端同环境，已装）：

```python
MongoClient(url, serverSelectionTimeoutMS=2000).admin.command("ping")
```

⚠️ **`pymongo` 默认懒连接**：不显式 `ping` 的话连不上也不报错。
必须 `ping`，且设**短超时**——默认 30 秒会让启动脚本卡住，看起来像"脚本死了"。

### 3.4 `ensure_database.py` 的边界

按"先检查 → 再最小修复 → 绝不越界"设计：

| 步骤 | 检查 | 失败时 |
|---|---|---|
| 1 | MySQL 服务连得上吗 | 报错并给排查方向（服务/端口/账号密码） |
| 2 | 库存在吗 | **创建**（唯一写操作） |
| 3 | 关键表在吗 | **只报告**（建表是 `main.py` 的职责） |
| 4 | 字典/种子数据在吗 | **只报告**（同上） |
| 5 | MongoDB 通吗 | **只报告**，且**不影响退出码**（门户不依赖它） |

**刻意不做的**（每条都是"越界会造成伤害"）：

| 不做 | 原因 |
|---|---|
| 不建表、不灌种子 | 那是 `main.py` 的职责，重叠会让人搞不清"谁负责" |
| 不执行 `backend/sql/knowledgemap.sql` | 含 `DROP TABLE`，会清空真实数据 |
| 不改已有库的字符集 | 可能损坏已有数据，必须由人决定 |
| **不提供 `--recreate` / `--force` / `--reset`** | 重建库是低频危险操作，值得你**自己手打 SQL**。一旦有这个按钮，迟早被误用（2026-10-07 已因"整表清空"丢过一次数据，见 `docs/14` §12.4） |
| 不启动/停止 Mongo | 见 §3.3 |
| **不引入 `subprocess` / `os.system`** | 脚本没有执行外部命令的能力，就**不可能**误删文件、误停服务。这条已固化为例用 |

**需要"重置到干净状态"时的替代做法**：换库名（`MySQL_DATABASE=knowledgemap_dev`），
旧库原样留着。比 `DROP` 安全得多，且可回退。

## 4. 结束方式（决策 3）

用户问得很准：**"Ctrl+C 终止"和"独立停止脚本"是两种不同设计，混用会出问题。**

| 方案 | 机制 | 风险 |
|---|---|---|
| **A. 前台运行 + Ctrl+C** | 脚本管两个子进程，捕获信号后一起优雅关闭 | 终端窗口被误关时，进程可能残留 |
| **B. 后台运行 + 独立停止脚本** | 写 PID 文件后退出，停止脚本按 PID 杀 | PID 文件会过期（进程崩了文件还在） |

### 4.1 采用：A 为主，B 作备选

**A 为主**：`dev-start` 前台运行，**一个终端窗口 = 一次开发会话**；
两个进程都作为子进程受管；捕获 INT/TERM 后按**特定顺序**收摊。

**B 作备选**：`dev-stop` 用于两种情况：

1. 终端窗口被误关、进程残留（此时 Ctrl+C 已没机会按）；
2. 想知道"现在什么在跑" → 用 `--status`（**只读**，最安全，建议先跑它）。

### 4.2 停止脚本按**端口**找进程，不用 PID 文件（用户明确要求）

用户原话：**"专门杀端口，PID 在重复拉起进程的情况下会变个不停"**。

这是对的——PID 会随进程反复拉起而变，基于它的记录很快过期，
**过期后可能杀到无关进程**。端口在这个项目里是更稳定的"身份"。

### 4.3 关闭顺序：先前端、后后端

理由：反过来的话 Vite 会看到后端断开，在终端刷一屏 `ECONNREFUSED`，日志很脏。
先关前端，后端静静退出。

### 4.4 ⚠️ Windows 孤儿进程坑（决策 4）

**`Ctrl+C` 在 Windows 上不总能可靠传播到子进程树**，Node（Vite）尤其容易变孤儿
（它自己还会 spawn 子进程）。所以：

| 平台 | 手段 |
|---|---|
| Windows | `taskkill /PID <pid> /T /F` —— **`/T` 杀整棵树** |
| Unix | `setsid` 起独立进程组 + `kill -TERM -<pgid>`（负号 = 整组） |

**这也是坚持要 B（停止脚本）的原因**——它不只是冗余，是兜底。

### 4.5 不杀"看起来不是本项目"的进程

`dev-stop` 判断占用者是否为项目进程：

- 命令行含项目根目录 → 本项目
- 命令行含 `main.py`（后端入口）或 `vite`（前端）→ 本项目
- 都不含 → **跳过并警告**，提示可加 `--force`

**为什么不能只看进程名**：机器上可能同时跑着别的 Node/Python 项目。
杀掉不相关的程序是事故，不是清理。

⚠️ **判断"是不是我们启的"不能只看项目根目录**：`dev-start` 启动前端用的是
**相对路径**（`node_modules/vite/bin/vite.js`），命令行里根本没有项目路径。
第一版只匹配项目路径，结果**把自己刚启的前端认成别人的**（实测踩到，见 §7.2）。

## 5. 平台脚本

### 5.1 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `-Check` / `--check` | **关闭** | 额外做前端类型检查与后端依赖检查（决策 5：默认关闭，开发时要快） |
| `-BackendPort` / `--backend-port` | 8010 | 后端端口 |
| `-FrontendPort` / `--frontend-port` | 3000 | 前端端口 |
| `-NoFrontend` / `--no-frontend` | 关闭 | 只起后端 |
| `-BackendEntry` / `--backend-entry` | `main.py` | 后端入口（便于测试与将来替换） |

`dev-stop.*` 额外有 `-Status` / `--status`（只读）与 `-Force` / `--force`。

### 5.2 启动流程（两个平台同构）

```
1. 解析 Python 解释器（KM_PYTHON 可覆盖）
2. 检查 backend/.env（缺失只提示，不阻止——database.py 有默认值）
3. 检查依赖（仅 -Check）
4. 检查端口占用 → 被占用则报错并停（打印占用者 PID/进程名）
5. 跑 ensure_database.py（建库 + 报告）
6. 起后端 → 轮询 /api/health 直到通过（默认 40 秒超时）
7. 起前端（Vite）
8. 前台守候 → 任一进程退出或 Ctrl+C 就一起收摊
```

**为什么要等健康检查**：不等的话，前端可能在后端就绪前起来，
用户打开页面看到一堆失败请求，误以为代码有问题。

**默认端口**：后端 8010（`main.py` 的 `KM_BACKEND_PORT`）、前端 3000（Vite 默认）。

### 5.3 文件清单

见 §9 的脚本表（那里带复跑命令，此处不重复）。

**复用、不改的**：`backend/sql/knowledgemap.sql`（只用于核对漂移）、
`main.py` 的建表与种子逻辑、`frontend/vite.config.ts` 的 `KM_API_TARGET`、
`scripts/knowledgemap_launcher.py`（Ubuntu 生产模式，与本脚本互不干扰）。

## 6. 测试

### 6.1 `ensure_database_cases.py`：钉住安全边界

`ensure_database.py` 是**唯一会写数据库**的地方（创建库），
而"初始化"与"破坏数据"只有一线之隔（`docs/14` §12.4 丢过数据）。
所以 §3.4 列的每条边界都有一条用例钉住：无破坏性 SQL、无
`--recreate`/`--force`/`--reset`/`--drop`、库名白名单校验、`--check` 不创建、
Mongo 只 ping 且有短超时、**不引入 `subprocess`/`os.system`/`os.popen`**、
复用 `app.database.DATABASE_URL`。

**40/40 通过**。

### 6.2 `shell_script_cases.py`：shell 语法与约定

用**真 `bash -n`** 检查语法——**不要手写 shell 结构检查器**：
第一版这么干，8 条里 7 条误报（heredoc 里的 Python 括号、
sed 表达式里的 `{0,1}`、行尾的 `do`）。**误报比没有检查更糟**，
它会训练人忽略警告。详见 §11.2 第 2、3 条。

**约定检查**——每条都对应一个真实 bug 或一条硬规则：

| 检查 | 为什么 |
|---|---|
| 前端启动不在子 shell 里 | 子 shell 里追加 `CHILD_PIDS`，**父 shell 收不到** → 前端变孤儿 |
| 注册了 `cleanup` trap 且绑定 INT/TERM | 否则 Ctrl+C 留孤儿 |
| 注入了 `KM_API_TARGET` / `KM_BACKEND_PORT` | 端口只决定一次（§3.2） |
| 停止脚本不依赖 `.pid` 文件、按端口定位 | §4.2 |
| `--status` 分支以 `exit 0` 结束 | 只读保证 |
| 不用 `pkill` / `killall` / `Stop-Process -Name` | 会误杀同机的同名进程 |
| Windows 用 `taskkill /T`、Unix 用进程组 | §4.4 |
| 调 Python 前设 `PYTHONIOENCODING` | 否则中文输出乱码（§7.3 第 1 条） |

**36/36 通过**。

## 10. 风险与边界

### 10.1 需长期注意

| # | 风险 | 说明 |
|---|---|---|
| R1 | **端口只决定一次这条不能破** | 若有人给前端加一个"自己探测后端端口"的逻辑，就会重新出现"页面能开但接口 404"。见 §3.2 |
| R2 | **`ensure_database.py` 不能加破坏性开关** | 见 §3.4。`--recreate` 这类按钮迟早被误用 |
| R3 | **停止脚本的"是否本项目"判断依赖入口特征** | 若将来把后端入口改名（不叫 `main.py`）或换掉 vite，这个判断会失效 → 会变成"跳过、不结束"。改入口时同步改 `is_ours` / `IsOurs` |
| R4 | **Windows 上 `taskkill /T` 是必需的** | 去掉 `/T` 会留下孤儿进程占着端口，且现象是"端口明明没服务却提示被占" |
| R5 | **Ubuntu 侧尚未端到端验证** | 见 §8。不阻塞当前开发（都在 Win11） |

### 10.2 有意保留的边界

| # | 项 | 说明 |
|---|---|---|
| R6 | 不自动启停 MongoDB | 它开机自启；脚本替用户改状态会掩盖"为什么它本来是停的"（§3.3） |
| R7 | 不自动启停 MySQL | 同上，且 Windows 上是系统服务 |
| R8 | 不杀"非本项目"的占用者 | 需要 `--force` 显式确认（§4.5） |
| R9 | 两个进程共用同一终端 | 日志会交织。换来"一个终端窗口 = 一次会话"的简单模型 |
| R10 | 与 `Start-KnowledgeMap.sh`（生产模式）并存 | 两者场景不同，不合并（§首段说明） |

### 11.2 工具链的坑

| # | 现象 | 根因与对策 |
|---|---|---|
| 1 | `Select-Object -First N` 之后退出码变成 1 | 它**提前关闭管道**，会杀掉还在写输出的子进程。用 `Out-String -Stream` 或完整读取来验证退出码 |
| 2 | `shutil.which("bash")` 拿到的不是真 bash | Windows 上可能返回 WSL 的**转发器**（`C:\Windows\system32\bash.exe`）；WSL 未装发行版时执行它报 `execvpe(/bin/bash) failed`，**看起来像脚本语法错，实际是环境问题**。对策：用 `bash -c "echo ok"` **验证它能真跑起来**；可用的真 bash 在 `C:\Program Files\Git\bin\bash.exe`（Git for Windows 自带，实测 5.2.37） |
| 3 | 手写 shell 结构检查器 8 条里 7 条误报 | heredoc 里的 Python 括号、sed 里的 `{0,1}`、行尾的 `do`。**改用真 `bash -n`**（§6.2） |
| 4 | 测试里断言"源码不含 `Start-Service`"失败 | 脚本的**提示文本**里正当地写着"你可以 `Start-Service MongoDB`"。字符串匹配分不清"建议"与"动作"——改为检查**能力**（有没有 `subprocess`） |
| 5 | `settings.TRADESIM_MONGO_URL` 不存在 | 字段名是 `MONGO_URL`；`TRADESIM_MONGO_URL` 是它读的**环境变量**名，不是属性名 |
